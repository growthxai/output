The `output` CLI is how you create projects, start development services, run workflows, and debug executions. It's the main way you interact with Output during development.

## Quick Start

```bash
# Create a new project
npx @outputai/cli init
cd <project-name>

# Start development services (Temporal, API, worker)
npx output dev

# Run a workflow with a test scenario
npx output workflow run lead_enrichment acme
```

### output dev

Start all development services via Docker Compose:

```bash
output dev
```

This starts:

| Service | URL | Description |
|---------|-----|-------------|
| **Temporal UI** | [http://localhost:8080](http://localhost:8080) | Monitor and debug workflows |
| **API Server** | [http://localhost:3001](http://localhost:3001) | REST API for running workflows |
| **Worker** | — | Processes workflows with auto-reload on `src/` changes |
| **PostgreSQL** | — | Temporal persistence (container-internal) |
| **Redis** | — | Caching layer (container-internal) |
| **Temporal Server** | — | gRPC endpoint (container-internal) |

| Flag | Default | Description |
|------|---------|-------------|
| `--compose-file, -f` | — | Path to custom docker-compose file |
| `--detached, -d` | false | Start services in the background and exit immediately |
| `--image-pull-policy` | `always` | Image pull policy: `always`, `missing`, or `never` |

<Note>
Worker hot-reload does not watch `package.json`. After adding or changing dependencies, run `npm install`, then bring the stack down and start `output dev` again so the worker container reinstalls into its `node_modules` volume. Quitting a foreground `output dev` that owns the stack tears it down and is enough; if the stack is still running (an attached session, or one started with `output dev -d`), run `output dev down` first, then `output dev` again.
</Note>

#### Running multiple dev stacks

You can run multiple isolated Output stacks on the same machine — useful when working across several projects simultaneously or testing against different versions.

Each stack needs a unique project name and non-conflicting host ports. Set these in the project's `.env`:

```bash
# Project A (.env) — defaults, no changes needed
DOCKER_SERVICE_NAME=project-a

# Project B (.env)
DOCKER_SERVICE_NAME=project-b
OUTPUT_CATALOG_ID=project-b
OUTPUT_API_HOST_PORT=3002
OUTPUT_TEMPORAL_UI_HOST_PORT=8081
OUTPUT_TEMPORAL_HOST_PORT=7234
```

`DOCKER_SERVICE_NAME` isolates Docker networks, volumes, and container names so the stacks don't interfere with each other. `OUTPUT_CATALOG_ID` keeps each stack's workflow catalog separate. The three `OUTPUT_*_HOST_PORT` vars control which ports are exposed on your machine — the container-internal ports are unchanged, so workers in either stack still reach Temporal at `temporal:7233`.

Run `npx output dev` in each project directory. Project A's API is at `http://localhost:3001` and Project B's at `http://localhost:3002`. If a port is already in use, `output dev` names the conflicting port and the env var to override.

#### Attaching to a running stack

If services are already running for this project, `output dev` attaches and
monitors them instead of reporting a port collision on our own containers.

An attached session does not own the stack: quitting the dashboard leaves the
services running. The footer reads `ctrl+c detach (keeps running)` so you can
tell which mode you're in. Stop an attached stack explicitly:

```bash
output dev down
```

A stack whose containers are all stopped is not an attach — `output dev` starts
it in the foreground and tears it down on quit, as a fresh start would.

### output fix

Align the project's `package.json` with the current project template:

```bash
output fix
```

The command adds missing Output scripts, replaces outdated ones, removes deprecated ones, replaces an `@outputai/output` dependency with `@outputai/core` (dependency) and `@outputai/cli` (dev dependency) at the same version, and drops `outputai.hookFiles` entries that point to `@outputai/credentials`. It prints the planned changes and asks for confirmation before writing. If dependencies changed, reinstall afterwards.

### output workflow start

Start a workflow asynchronously — returns the workflow ID immediately without waiting:

```bash
output workflow start <workflowName> [scenario]
```

<ParamField path="workflowName" type="string" required>
  Name of the workflow to start
</ParamField>

<ParamField path="scenario" type="string">
  Scenario name — resolved from the workflow's scenarios/ directory
</ParamField>

| Flag | Default | Description |
|------|---------|-------------|
| `--input, -i` | — | JSON input or file path (overrides scenario) |
| `--catalog, -c` | `OUTPUT_CATALOG_ID` | Catalog name (the deprecated `--task-queue, -q` aliases still work) |
| `--search-attributes, -a` | — | Temporal [search attributes](/operations/deployment#search-attributes) as a JSON object or file path |
| `--monitor, -m` | false | Attach after starting and stream status updates until the workflow ends |

Add `--monitor` to start a workflow and watch it in one command, instead of
copying the workflow ID into a separate [`workflow monitor`](#output-workflow-monitor) call:

```bash
output workflow start lead_enrichment --input ./test_input.json --monitor
```

```text
Starting workflow: lead_enrichment...

Workflow started successfully

Workflow ID: wf-12345

Monitoring wf-12345 (run 2fe0b36b-...)... (Ctrl+C to detach)
● Fetch Company running…
✓ Fetch Company  1.2s
● Score Lead running…
✓ Score Lead  3.4s
✓ workflow completed · 4.8s

Use "workflow result wf-12345" to get the workflow result
```

Monitoring attaches to the exact run that was just started, so a rapid re-start
can't leave you watching a different execution. Everything else matches
`workflow monitor` — Ctrl+C detaches without stopping the workflow (exit `130`),
and the command exits `1` if the workflow fails.

The stream reports progress, not the return value, so the command closes by
naming the follow-up: [`workflow result`](#output-workflow-result) after a run
that completed, [`workflow debug`](#output-workflow-debug) after one that failed.

If monitoring itself drops — the API restarts, the connection resets — a
transient failure is retried a few times before the command gives up. Once it
does, the workflow it started keeps running, so the command says so and exits
`3` rather than `1`. Retry logic keyed on a failed workflow therefore can't
re-submit a workflow that is already in flight:

```text
Warning: Poll failed (1/5), retrying: fetch failed
Warning: Poll failed (2/5), retrying: fetch failed
Warning: Poll failed (3/5), retrying: fetch failed
Warning: Poll failed (4/5), retrying: fetch failed
Error: Workflow wf-12345 started, but monitoring stopped:
Connection refused to http://localhost:3001. Is the API server running?
The workflow is still running. Use "workflow status wf-12345" to check on it.
```

`--monitor` cannot be combined with `--json`. Under `--json` the CLI suppresses
progress output and prints a single JSON object when the command finishes, which
would silently swallow every streamed update and leave the command looking hung
until the workflow ended. Use `workflow run --json` to wait for a result as JSON,
or `workflow monitor <id> --format json` to stream newline-delimited JSON.

These flags tune the stream and require `--monitor`:

| Flag | Default | Description |
|------|---------|-------------|
| `--interval` | 2500 | Poll interval in milliseconds |
| `--include-payloads` | false | Include decoded step input/output payloads |
| `--color` | true | Colorize status output (`--no-color` to disable) |

### output workflow monitor

Attach to a workflow run and stream status updates until it ends — a step
starts, completes, or fails is printed as it happens, so you don't have to
re-run `workflow status` in a loop to watch a long-running workflow:

```bash
output workflow monitor <workflowId>
```

<ParamField path="workflowId" type="string" required>
  The workflow execution ID
</ParamField>

| Flag | Default | Description |
|------|---------|-------------|
| `--run-id, -r` | latest run | Monitor a specific run (continue-as-new chains are followed regardless of this flag) |
| `--format, -f` | text | Output format: json, text |
| `--include-payloads` | false | Include decoded step input/output payloads |
| `--interval` | 2500 | Poll interval in milliseconds. Also bounds the resumed long-poll's server-side wait, so an idle workflow's update cadence is roughly twice this value, not a longer separate server default. |
| `--color` | true | Colorize status output (`--no-color` to disable) |

Exits `0` when the workflow completes, `1` when it fails, is canceled,
terminated, or times out, and `130` if you detach with Ctrl+C — detaching
never stops the workflow itself. `monitor` also exits `1` after 5 consecutive
transient poll failures (network errors, 5xx/408/429 responses), printing a
warning before each retry — this is API/network trouble, not a workflow
outcome, but shares the same exit code.

```bash
output workflow monitor wf-12345
output workflow monitor wf-12345 --run-id 2fe0b36b-...
output workflow monitor wf-12345 --format json
```

To start a workflow and attach in a single step, use
[`workflow start --monitor`](#output-workflow-start) instead of copying the ID
between two commands.

<Note>
  `--format json` here is **not** the same thing as the native `--json` flag used by `workflow run`, `workflow status`, and other commands migrated in OUT-419 (see the [changelog](/changelog)). Native `--json` suppresses all in-progress log output and prints a single JSON object once the command finishes. `monitor` has no single final result to print — it's a long-running command that emits a stream of discrete events (a step starting or finishing, a continue-as-new notice, a final summary) while the workflow is still running. `--format json` prints each event as its own line of newline-delimited JSON as it happens, so the output can be piped into `jq` or read incrementally by another process — often another automated or agent process rather than a person, which is the primary reason this command keeps its own JSON mode instead of adopting `--json`.
</Note>

### output workflow result


  The workflow execution ID
</ParamField>

#### Workflow result JSON format

Use `--json` with `output workflow run` or `output workflow result` to print the full structured workflow result:

```json
{
  "v": "2",
  "workflowId": "lead_enrichment-a1b2c3d4-5678-90ab-cdef-1234567890ab",
  "runId": "b5c6d7e8-9012-3456-7890-abcdef123456",
  "status": "completed",
  "input": { "companyDomain": "acme.com" },
  "output": {
    "company": "Acme Corp",
    "summary": "Enterprise software company focused on..."
  },
  "trace": {
    "local": "/path/to/trace.json",
    "remote": "s3://trace-bucket/path/to/trace.json"
  },
  "error": null
}
```

| Field | Description |
|-------|-------------|
| `v` | Workflow result payload version. Current responses use `"2"`. |
| `workflowId` | Workflow execution ID. |
| `runId` | Specific Temporal run ID. |
| `status` | Current or final execution status. |
| `input` | Original workflow input. |
| `output` | Value returned by the workflow on success, or `null` on failure. |
| `trace` | Trace metadata for the run, or `null` when unavailable. |
| `error` | Serialized error object on failure, otherwise `null`. It includes `name` and `message` and may contain `activityType`, `cause`, and other diagnostic properties. |

#### JSON error format

When a command run with `--json` fails, it writes a JSON error to **stderr** and leaves stdout empty, so a script can read results from stdout and failures from stderr without mixing them. This applies to `run`, `start`, `status`, `result`, `list`, `runs list`, `cost`, `input`, `test`, and `dataset list`. `debug` always prints JSON on stdout and reports failures as plain text on stderr with a non-zero exit code.

```json
{
  "error": {
    "message": "Workflow not found. Check the workflow ID.",
    "status": 404
  }
}
```

| Field | Description |
|-------|-------------|
| `message` | Human-readable description of the failure. Always present. |
| `status` | HTTP status returned by the API. Present only when the API responded. |
| `code` | System error code, such as a network error code. Present only when the failure has one. |

The exit code tells you what kind of failure it was, and is the same as in text mode: `1` for API and network failures, and `2` for usage errors such as invalid flag combinations on `workflow start`. Without `--json`, errors are printed as plain text, as before.

### output workflow reset

Rerun a workflow from after a specific completed step. The current run is terminated and a new run is created that replays up to the given step (reusing its output), then re-executes every step after it. Useful when iterating on a late step without re-paying the cost of earlier LLM or API calls:

```bash
output workflow reset <workflowId> --step <stepName>
output workflow reset lead_enrichment-a1b2c3d4 --step consolidateCompetitors --reason "Retry with updated prompt"
```

<ParamField path="workflowId" type="string" required>
  The workflow execution ID
</ParamField>

| Flag | Default | Description |
|------|---------|-------------|
| `--step, -s` | — | **Required.** Name of the completed step to reset after. The step itself is not re-executed; every step after it is. |
| `--reason, -r` | — | Free-text reason, recorded in Temporal history for auditability |

The command prints the original `workflowId` and a new `runId` for the fresh execution. Use `output workflow status <workflowId>` and `output workflow result <workflowId>` to track it.

<Tip>
Find valid step names with `output workflow debug <workflowId>`. A step is an activity named `<workflowName>#<stepName>`, and the `--step` value is the part after the `#`. To list them: `output workflow debug <workflowId> | jq -r '.workflows[0].events[] | select(.eventType == "EVENT_TYPE_ACTIVITY_TASK_SCHEDULED") | .activityTaskScheduledEventAttributes.activityType.name'`.
</Tip>

### output workflow debug

Read one workflow run from Temporal and print its history, for debugging. The output is one JSON document with an entry for every workflow: the one you asked for, then each child workflow it started. Every entry holds that workflow's own Temporal history events. The command talks to Temporal directly, so it needs no API, no trace files and no S3, and it behaves the same in development and production.

```bash
output workflow debug <workflowId>
output workflow debug wf-12345 --run-id 11111111-2222-4333-8444-555555555555
output workflow debug wf-12345 --profile prod
output workflow debug wf-12345 --address temporal.internal:7233 --namespace staging
```

<ParamField path="workflowId" type="string" required>
  The workflow execution ID (the id printed by `workflow start`, not the workflow name)
</ParamField>

<Note>
  Generated workflow ids can start with `-`, and the CLI then reads the id as a flag (`Nonexistent flag: -Ab...`). Quoting does not help, because the shell removes the quotes. Put `--` before the id: `output workflow debug --address localhost:7233 -- -Ab...`. The same applies to every command that takes a workflow id.
</Note>

| Flag | Default | Description |
|------|---------|-------------|
| `--run-id`, `-r` | latest run | Run to start from. Every reset, retry or continue-as-new has its own run id. The runs that continue from it are read too; the entry always states the run that was read. |
| `--profile` | `default` | Temporal profile to read from `temporal.toml` |
| `--address` | `localhost:7233` | Temporal server address. The default follows `OUTPUT_TEMPORAL_HOST_PORT`, so it matches the port `output dev` publishes |
| `--namespace` | `default` | Temporal namespace |

The output is always JSON. `--json` is accepted and does nothing, so scripts that pass it keep working.

#### Connecting to Temporal

Connection settings follow Temporal's standard client configuration, the same one the `temporal` CLI uses, so one profile file can point `workflow debug` at any backend. Highest priority first:

1. The `--address` and `--namespace` flags
2. Environment variables: `TEMPORAL_ADDRESS`, `TEMPORAL_NAMESPACE`, `TEMPORAL_API_KEY` and the other `TEMPORAL_*` variables Temporal defines for TLS
3. The profile chosen with `--profile` (or `TEMPORAL_PROFILE`, then `default`) in `temporal.toml`
4. The defaults: `localhost:` plus the dev stack's Temporal port (`OUTPUT_TEMPORAL_HOST_PORT`, `7233` unless overridden), and the namespace `default`

`temporal.toml` lives in `temporalio/` under your user config directory (`~/Library/Application Support` on macOS, `$XDG_CONFIG_HOME` or `~/.config` on Linux, `%APPDATA%` on Windows). Set `TEMPORAL_CONFIG_FILE` to use another path.

```toml
[profile.default]
address = "localhost:7233"
namespace = "default"

[profile.prod]
address = "my-namespace.a2b3c.tmprl.cloud:7233"
namespace = "my-namespace.a2b3c"
api_key = "..."
```

An explicit `--profile` that does not exist is an error. API keys and TLS material come only from the profile or the environment, never from a flag.

<Warning>
The profile's credentials stay attached when you override the address. `--profile prod --address other:7233` sends the `prod` API key to `other:7233`, and so does `TEMPORAL_ADDRESS`. Override the address only with hosts you trust.
</Warning>

#### Output

The output is compact JSON on a single line, with a summary first and then the workflows. Pipe it to `jq .` to read it indented, or to `jq -c '.workflows[].events[]'` to get one event per line. It is shown split over several lines below:

```json
{
"complete":true,
"warnings":[],
"temporal":{"address":"localhost:7233","namespace":"default"},
"workflows":[
{"workflowId":"Ra-DSZCo4qbKQIyTXL6AN","runId":"01a1f420-38e7-7df8-b667-ef005eca9993","workflowType":"nested_parallel_children","status":"WORKFLOW_EXECUTION_STATUS_COMPLETED","pendingActivities":[],"pendingChildren":[],
"events":[
{"eventId":"1","eventTime":"2026-11-19T14:05:14.855915962Z","eventType":"EVENT_TYPE_WORKFLOW_EXECUTION_STARTED",...},
...
]},
{"workflowId":"Ra-DSZCo4qbKQIyTXL6AN-B_eQB5h2dPvZwr4kpzbvbc","runId":"...","workflowType":"nested_parallel_children_child","status":"WORKFLOW_EXECUTION_STATUS_COMPLETED","parent":{"workflowId":"Ra-DSZCo4qbKQIyTXL6AN","runId":"01a1f420-38e7-7df8-b667-ef005eca9993"},"pendingActivities":[],"pendingChildren":[],
"events":[
...
]}
]
}
```

At the top:

- `complete` is `true` when everything was read. Scripts should check this and nothing else.
- `warnings` is a list of sentences about what could not be read (see below). It is empty when `complete` is `true`. The wording can change, so do not parse it.
- `temporal` is the address and namespace that were used.

Each entry in `workflows` has:

- `workflowId`, `runId` and `workflowType`.
- `status`, Temporal's name for it: `WORKFLOW_EXECUTION_STATUS_RUNNING`, `..._COMPLETED`, `..._FAILED`, `..._CANCELED`, `..._TERMINATED`, `..._CONTINUED_AS_NEW` or `..._TIMED_OUT`. It is `null` for a workflow that was not read.
- `parent` (`workflowId` and `runId`), on child workflows only.
- `pendingActivities` is what shows a stuck run: each entry has the activity, its state, its attempt number and the last failure. `pendingChildren` lists the child workflows Temporal reports as open when it describes the workflow, each as `{ workflowId, runId, workflowType }`. On a closed parent that list can be out of date, so take a child's status from its own entry. `status` and both pending lists are read after the events, so they are never older than the events. A running workflow shows `WORKFLOW_EXECUTION_STATUS_RUNNING` with no closing event, which is how you debug it live. If a workflow finishes while it is being read, a warning says its events stop before the end, and running the command again gives the full history.
- `events`, the history, last in the entry.

The first entry is the workflow you asked for. Children follow in the order their parent reports them started, and every child, however deep, is in the same flat list. A workflow that uses `continueAsNew` has one entry per run, all with the same `workflowId` (and the same `parent`, for a child) and different `runId`s. Entries are ordered by when they started, so a run follows the run that continued into it. Runs of the workflow you asked for have no `parent`.

For a step that failed once and is waiting to retry, `pendingActivities` looks like this:

```json
"pendingActivities":[{"activityId":"2","activityType":"error_step#thrower","state":"PENDING_ACTIVITY_STATE_SCHEDULED","attempt":2,"lastFailure":{"message":"Foo","source":"TypeScriptSDK","stackTrace":"Error: Foo\n    at fn (...)","applicationFailureInfo":{"type":"Error"}}}]
```

Events are exactly what Temporal's own JSON renders (the same shape the Temporal UI exports), and the command adds nothing to them: `EVENT_TYPE_*` names, string ids, ISO timestamps, durations like `"30s"`, and attributes under `<eventName>EventAttributes`.

```json
{"eventId":"13","eventTime":"2026-11-19T13:17:33.285380763Z","eventType":"EVENT_TYPE_ACTIVITY_TASK_SCHEDULED","taskId":"34603040","activityTaskScheduledEventAttributes":{"activityId":"2","activityType":{"name":"simple#sumValues"},"taskQueue":{"name":"main","kind":"TASK_QUEUE_KIND_NORMAL"},"header":{...},"input":{"payloads":[{"values":[1,2,3]}]},"startToCloseTimeout":"1200s"}},
{"eventId":"15","eventTime":"2026-11-19T13:17:33.292884513Z","eventType":"EVENT_TYPE_ACTIVITY_TASK_COMPLETED","taskId":"34603048","activityTaskCompletedEventAttributes":{"result":{"payloads":[6]},"scheduledEventId":"13","startedEventId":"14"}},
```

- Payloads (inputs, results, failure details, memo) are decoded from Temporal's base64 form into plain JSON and truncated, see below.
- Event ids restart in every workflow, so an event is identified by its workflow entry plus `eventId`.
- Related events point at each other through ids such as `scheduledEventId` and `startedEventId`. The command does not pair them or compute durations, statuses or attempts.
- Steps are activities named `<workflowName>#<stepName>`. Activities named `__internal#...` belong to the framework.
- A parent's `EVENT_TYPE_CHILD_WORKFLOW_EXECUTION_*` events mark where each child started and ended, and they name the child. The child's own entry holds the child's events.
- A step that throws shows its error as `failure` (`message`, `source`, `stackTrace`, `applicationFailureInfo.type` and `details`) on `EVENT_TYPE_ACTIVITY_TASK_FAILED`. The workflow then ends with `EVENT_TYPE_WORKFLOW_EXECUTION_FAILED`, whose `failure.cause` chain holds the same error. With a child workflow, the child's own failed event is followed by the parent's `EVENT_TYPE_CHILD_WORKFLOW_EXECUTION_FAILED` with the cause nested one level deeper.
- Every run that continues as new ends with `EVENT_TYPE_WORKFLOW_EXECUTION_CONTINUED_AS_NEW` and its `newExecutionRunId`. The next run is read automatically and gets its own entry, so the chain from the run you start at is in the output, and the page limit below applies to all of it. Without `--run-id` you start at the latest run, so there is no chain after it; pass the first run's id to read the whole chain.
- Payloads that cannot be decoded, for example when you use an encryption codec, print as `[Undecodable Payload: <encoding>]`.

The output works with `jq`:

```bash
# Is everything here, and what is missing?
output workflow debug wf-12345 | jq '.complete, .warnings'

# Failures, with the workflow they happened in
output workflow debug wf-12345 | jq -c '.workflows[] | .workflowId as $w | .events[] | select(.eventType == "EVENT_TYPE_ACTIVITY_TASK_FAILED") | {workflowId: $w} + .'

# Child workflows and their status
output workflow debug wf-12345 | jq -c '.workflows[] | select(.parent) | {workflowId, status, parent: .parent.workflowId}'

# The steps that ran, per workflow
output workflow debug wf-12345 | jq -r '.workflows[] | .workflowId as $w | .events[] | select(.eventType == "EVENT_TYPE_ACTIVITY_TASK_SCHEDULED") | "\($w) \(.activityTaskScheduledEventAttributes.activityType.name)"'
```

Events are grouped by workflow and not merged, so the output has no single timeline. When you need to see what the parent and its children did at the same moment, build one:

```bash
output workflow debug wf-12345 | jq '[.workflows[] | .workflowId as $w | .events[] | . + {_workflowId: $w}] | sort_by(.eventTime | sub("Z$"; "") | [ .[0:19], ((.[20:] // "") + "000000000")[0:9] ])'
```

#### Truncation

Long values are cut so a large LLM response does not bury the failure. The limits always apply, there is no flag to lift them, and full payloads stay in Temporal:

| Value | Limit | Marker |
|-------|-------|--------|
| Strings over 1,024 characters | first 1,000 and last 24 characters | `<head>... [N more characters omitted] ...<tail>` |
| Arrays | first 20 items | `... [N more items omitted]` |
| Objects | first 50 keys | `[Maximum Object Properties Reached]` |
| Nesting | 10 levels | `[Maximum Depth Reached]` |
| Values in one payload | 1,000 | `[Serialization Limit Reached]` |

Error stacks keep their first 10 lines. Error messages are never cut. Nothing is redacted: the output contains what your workflow handled.

#### Long histories and missing children

The run and its children are read to the end. Reading stops after 100,000 events or 1,000 pages (of 1,000 events) across the whole tree, whichever comes first. A single Temporal history never exceeds about 51,200 events. When it stops early, or when a child's history is gone (Temporal deletes closed histories after the namespace retention period), the output still succeeds. `complete` is `false` and `warnings` says what is missing, naming each workflow:

```json
"complete":false,
"warnings":[
"Child workflow Ra-DSZ...-B_eQB (run 01a1f420-...) was not read: the limit of 100000 events for the whole tree was reached. Its entry has no events.",
"Child workflow Ra-DSZ...-C3kp5 (run 01a1f420-...) is no longer in Temporal: closed histories are deleted after the namespace retention period. Its entry has no events."
],
```

A child workflow or later run whose history cannot be read for another reason, such as a permission or network error, is reported the same way, with the error message in the warning:

```json
"Child workflow Ra-DSZ...-D9qlx (run 01a1f420-...) could not be read: 7 PERMISSION_DENIED: ... Its entry has no events."
```

A workflow that was not read (its history is gone, it could not be read, or the limit was reached first) still has an entry, with `events` empty, `status` set to `null` and empty `pendingActivities` and `pendingChildren`. When the limit is reached in the middle of a workflow's history, its entry keeps the events read so far and a warning says it was read only in part. If a workflow's status and pending lists cannot be read, its events are kept and a warning says they may be missing or out of date.

#### Errors and exit codes

Standard behavior: stdout carries only data, errors go to stderr, and a failure exits non-zero with nothing on stdout. That covers a workflow or run that is not found, a Temporal server that cannot be reached or does not answer within 30 seconds, a missing profile and a bad namespace, and failing to read the first page of the workflow you asked for. Failures on children and later runs are warnings instead. A partial result (`complete` is `false`) exits `0`.

<Note>
Temporal's history records an activity's start only for the attempt that ran last. Earlier attempts do not have their own events. The last retry shows up as `attempt` and `lastFailure` on `EVENT_TYPE_ACTIVITY_TASK_STARTED` (the failure of the attempt before it), and on `pendingActivities` while the step is still retrying.
</Note>

<ParamField path="workflowId" type="string" required>

### output workflow dataset generate

Generate a dataset case for a workflow from a scenario, inline JSON, or a completed run read from Temporal:

```bash
output workflow dataset generate <workflowName> [scenario]
output workflow dataset generate <workflowName> --workflow-id <workflowId> [--run-id <runId>]
```

<ParamField path="workflowName" type="string" required>
  Name of the workflow (its type). It decides which workflow's `tests/datasets` directory the case is written to
</ParamField>

<ParamField path="scenario" type="string">
  Scenario name — resolved from the workflow's scenarios/ directory
</ParamField>

| Flag | Default | Description |
|------|---------|-------------|
| `--input, -i` | — | Workflow input as JSON string or file path (overrides scenario) |
| `--name, -n` | — | Dataset name (defaults to the scenario name, or the workflow id with `--workflow-id`) |
| `--workflow-id` | — | Workflow id of a completed run to read from Temporal (the id printed by `workflow start`, not the workflow name). Cannot be combined with a scenario or `--input` |
| `--run-id, -r` | latest run | Run to read. Needs `--workflow-id` |
| `--catalog, -c` | `OUTPUT_CATALOG_ID` | Catalog the workflow runs on (scenario and `--input` modes) |
| `--profile` | `default` | Temporal profile to read from `temporal.toml` (with `--workflow-id`) |
| `--address` | `localhost:7233` | Temporal server address (with `--workflow-id`) |
| `--namespace` | `default` | Temporal namespace (with `--workflow-id`) |

With `--workflow-id`, the command reads the run's start input and its result from Temporal and writes them as a case. It connects the same way as [`workflow debug`](#output-workflow-debug), so it works on local and remote Temporal. Values are not truncated, and secrets are redacted as in the other modes. The run must be a completed run of `<workflowName>`, given by its own name and not by an alias: a run of another workflow, a run that is still running or failed, a run that is missing or an unreachable Temporal stops the command with a message and writes nothing. A run that continued as new is not completed, so omit `--run-id` or pass the run id of the last run. When the run is a continuation of earlier runs, the case takes the input of the first run of the chain, because a continuation run only holds the continuation arguments, and the result of the run read. The command prints the run ids it used, and fails if the first run can no longer be read. A run that started without input is saved with an empty input, and a run that returned nothing is saved with a `null` output. If the dataset file already has a case with that name, its `input` and `last_output` are replaced and its other fields (such as `ground_truth`) are kept. The file goes to the workflow's `tests/datasets` directory. The folder is looked up as `src/workflows/<workflowName>` or `workflows/<workflowName>` under the current directory (or under `OUTPUT_WORKFLOWS_DIR`), and for a nested workflow through the API's workflow catalog. If neither finds it, for example for a nested workflow when the API is not reachable, the case is written to a new `src/workflows/<workflowName>/tests/datasets` folder.

```bash
# Generate from a scenario
output workflow dataset generate simple basic_input

# Generate with inline JSON input
output workflow dataset generate simple --input '{"values": [1, 2, 3]}' --name custom_case

# Generate from a completed run, read from Temporal
output workflow dataset generate simple --workflow-id wf-12345 --name from_run

# Generate from a specific run, on another Temporal
output workflow dataset generate simple --workflow-id wf-12345 --run-id 11111111-2222-4333-8444-555555555555 --profile prod
```

## Credentials Commands

These commands manage the encrypted credentials files read by [`@outputai/core/credentials`](/packages/core/credentials). Every command targets the global credentials by default and accepts these flags to pick another scope:

| Flag | Default | Description |
|------|---------|-------------|
| `--environment, -e` | - | Target environment (e.g. `production`, `development`) |
| `--workflow, -w` | - | Target a specific workflow directory |

<Note>
`--environment` and `--workflow` are mutually exclusive.
</Note>

### output credentials init

Create an encryption key and an encrypted credentials file:

```bash
output credentials init
```

| Flag | Default | Description |
|------|---------|-------------|
| `--force, -f` | false | Overwrite existing credentials |

### output credentials edit

Decrypt the credentials file, open it in `$EDITOR`, and re-encrypt it on save:

```bash
output credentials edit
```

| Flag | Default | Description |
|------|---------|-------------|
| `--force, -f` | false | When the current key can't decrypt the file, start from an empty file and re-encrypt with the current key (discards existing values) |

### output credentials set

Set a credential value by dot-notation path:

```bash
output credentials set <path> <value>
```

<ParamField path="path" type="string" required>
  Dot-notation path to the credential (e.g. `anthropic.api_key`)
</ParamField>

<ParamField path="value" type="string" required>
  Value to set
</ParamField>

| Flag | Default | Description |
|------|---------|-------------|
| `--yes, -y` | false | Skip the confirmation prompt when overwriting a value of a different shape |
| `--force, -f` | false | Re-encrypt with the current key even if it can't decrypt the existing file (discards existing values) |

### output credentials get

Print a single credential value by dot-notation path:

```bash
output credentials get <path>
```

<ParamField path="path" type="string" required>
  Dot-notation path to the credential (e.g. `anthropic.api_key`)
</ParamField>

### output credentials show

Print all decrypted credentials, for debugging:

```bash
output credentials show
```

```bash
# Initialize production credentials
output credentials init --environment production

# Initialize workflow-specific credentials
output credentials init --workflow payment_processing

# Edit production credentials
output credentials edit -e production

# Set a value without opening an editor
output credentials set anthropic.api_key sk-ant-xxxxx

# Get a workflow-specific credential
output credentials get stripe.secret_key --workflow payment_processing
```

## Environment Configuration

By default, the CLI loads environment variables from `.env` in the current directory. To use a different env file:

```bash
# Use production environment
OUTPUT_CLI_ENV=.env.prod output workflow list

# Use staging environment
OUTPUT_CLI_ENV=.env.staging output workflow run lead_enrichment acme
```

| Variable | Default | Description |
|----------|---------|-------------|
| `OUTPUT_CLI_ENV` | `.env` | Path to custom env file (relative or absolute) |
| `OUTPUT_API_URL` | `http://localhost:3001` | Output API server URL used by workflow commands (`workflow debug` talks to Temporal directly instead) |
| `OUTPUT_API_AUTH_TOKEN` | — | API auth token for requests (required in production) |
| `TEMPORAL_ADDRESS`, `TEMPORAL_NAMESPACE`, `TEMPORAL_API_KEY` | `localhost:7233`, `default`, — | Temporal connection for commands that read Temporal directly (`workflow debug`). Override the profile; the `--address` and `--namespace` flags override these |
| `TEMPORAL_PROFILE`, `TEMPORAL_CONFIG_FILE` | `default`, `temporal.toml` in the user config directory | Profile and file the Temporal connection is read from. See [`workflow debug`](#output-workflow-debug) |
| `OUTPUT_DEBUG` | — | Set to `true` to enable CLI debug mode |
| `DOCKER_SERVICE_NAME` | `output-sdk` | Docker Compose project name for `output dev` — isolates containers, networks, and volumes |
| `OUTPUT_API_HOST_PORT` | `3001` | Host port for the Output API server |
| `OUTPUT_TEMPORAL_UI_HOST_PORT` | `8080` | Host port for the Temporal UI |
| `OUTPUT_TEMPORAL_HOST_PORT` | `7233` | Host port for the Temporal gRPC endpoint. Override to run multiple dev stacks side-by-side. `workflow debug` uses it for its default address |
| `OUTPUT_API_VERSION` | Installed CLI version | API Docker image tag. Set to `dev` for local builds |
| `OUTPUT_WORKFLOWS_DIR` | `.` | Workflows subdirectory relative to project root. Set to `test_workflows` for monorepo dev |
| `ANTHROPIC_API_KEY` | — | Anthropic API key for AI-assisted workflow generation (`workflow plan`, `workflow generate`) |
